# PeerTTY 0.3 系列验证记录

## 0.3.0 授权与多终端

| 验证范围 | 实际结果 |
| --- | --- |
| 本机 macOS 伪终端 | 打开菜单和帮助，标题只显示一次。签发 24 小时邀请后给菜单进程发送 SIGHUP，重开可看到待批准状态和原邀请路径。在另一个空闲菜单中，授权和撤销的状态均自动出现，全程无需输入查询命令。 |
| Mac 原生 SSH 命令 | 两个独立后台授权进程通过回环测试服务配对。调用 `peertty link -- marker-exit` 获得预定的标准输出，进程退出码与远端返回的 7 相同。 |
| 已有 SSH 服务的 Linux 账号 | 在现有回环 22 监听旁，以不同的临时端口完成本次公钥登录，`id -un` 返回批准账号。原生 SSH 服务的 PID 在测试前后均为 1984。 |
| 角色、签名及到期 | 未批准的连接、另一台设备的本机证书、被替换的 SSH 公钥和跨邀请回执均被拒绝。两条已建立的流在撤销或短期授权到期后回收。 |
| 剪贴板与时长 | Linux 上用独立的 Wayland 命令夹具核对复制与读取的完整凭证。菜单用例覆盖默认 1 小时及 1、24 小时边界，0、25 和小数重新提示。 |
| 安装包 | Mac 当前用户命令已升级到 0.3.0。发布目录中的八项文件通过 SHA-256 校验。解包得到的 Windows 两个架构程序分别与对应发布二进制一致。原生 Windows 登录和系统剪贴板尚待实机验证。 |

## 双私网实测

两台独立的 Ubuntu ARM64 虚拟机运行发布版 0.3.0。下表六个场景均得到预期结果。

| 网络与被控端初始状态 | 结果 |
| --- | --- |
| 双 NAT，第一个 STUN 无响应，回执延迟 40 秒 | 备用 STUN 建立直连，两窗口均能登录。 |
| 双 NAT，两侧网关改写源端口 | 两端均选择 `udp srflx/srflx`，登录成功。 |
| 高延迟双 NAT，双向分别丢包 12% 和 22%，已有 SSH | 两窗口能同时使用。关闭两窗口及控制菜单后，新的 `peertty link -- id -un` 返回原授权账号。 |
| 相同弱网，两台机器互换角色，被控端 22 关闭 | 批准后用本次临时公钥免密登录，重开被控菜单显示现有连接。打开第二窗口后显示 2 个终端。在线撤销断开两路，后续 `link` 被拒绝。 |
| 两侧网关按目的地分配不兼容的端口 | 两端均能取得 STUN 映射，程序报告直连失败，业务 22 保持关闭。 |
| 网关封锁全部业务 UDP | 两端 STUN 映射均为 0，程序报告直连失败，业务 22 保持关闭。 |

四个成功场景均校验了原生 SSH 的 PTY 和远端账号。测试结束后，`engineer` 的业务 22 监听和连接数均为 0，`device` 原 SSH 服务 PID 仍为 1984，已建立连接为 0。两台机的本轮临时目录均已回收，实验网络恢复为测试前的弱网双 NAT。

```sh
go vet ./...
go test -race ./...
./lab/ctl punch-check --binary dist/peertty-linux-arm64
```

## 0.3.1 普通账号与 sudo

两台 Linux 靶机互换角色，使用原有的弱网双 NAT 和各自的 sudo 规则。先从被控机核对该账号能否以 root 执行 `/usr/bin/id -u`，再经 PeerTTY 分别用默认命令模式和 `link -t` 查询。两种模式均检查了远端终端类型、普通账号 UID、sudo 执行结果和退出码。

| 被控账号 | 两种模式的结果 |
| --- | --- |
| `engineer` 上的普通账号，UID 501，本机允许该命令 | 登录 UID 为 501，`sudo -n -u root -- /usr/bin/id -u` 输出 0，退出码为 0。 |
| `device` 上的 `ptlab`，UID 1000，本机未授权该命令 | 登录 UID 为 1000，sudo 返回退出码 1。 |

两轮均从被控端撤销授权，之后再次 `link` 被拒绝。两台靶机的临时目录和业务 SSH 连接数归零，`device` 原 SSH 服务 PID 保持 1984。测试使用已有的非交互规则，未进行真实密码输入。Mac 原生 OpenSSH 用例校验了单命令的 PTY 请求、脚本输出和远端退出码。Windows x64 和 ARM64 安装包已解包校验。

```sh
./lab/ctl menu-check --closed-ssh --revoke --check-sudo --binary dist/peertty-linux-arm64
./lab/ctl menu-check --revoke --check-sudo --binary dist/peertty-linux-arm64
```

## 0.3.1 双终端撤销与自然到期

两台独立的 Ubuntu ARM64 靶机在弱网双 NAT 下运行 0.3.1 发布版。每轮分别在菜单自动打开的 SSH 窗口和另一个 `peertty link` 窗口向同一文件写入一行。关闭并重开被控菜单后可以查看实时终端数。

| 结束方式 | 双机实测结果 |
| --- | --- |
| `engineer` 控制 `device`，被控方主动撤销 | `ptlab` 的两个 SSH 窗口均断开，再次 `link` 被拒绝。原 SSH 服务的 PID 仍为 1984。 |
| `device` 控制 `engineer`，签名邀请在 180 秒后自然到期 | 到期前状态显示 2 个终端，到期后两个窗口均断开，再次 `link` 被拒绝。被控端业务 22 端口恢复到初始关闭状态。 |

两轮结束后，两端均报告没有有效授权。通过独立的虚拟机管理通道读回了两个窗口写入的 `window-1` 和 `window-2`，随后测试脚本清理了该文件。在 `device` 的交互式 SSH 窗口，目标机的 sudo 显示了密码提示。测试在提示处取消，未输入真实密码，命令退出码为 1。

虚拟机的系统时间会在测试期间调整。自然到期用例同时记录两端墙钟和单调时钟。此次观察到两个窗口退出时，被控端墙钟已超过签名截止点 227 毫秒，控制端单调时钟已超过其计时截止点 334 毫秒。180 秒时长只用于这项实验，正常菜单仍提供 1–24 小时。

测试结束时，两台靶机业务端口 22 的已建立连接数均为 0，本轮临时目录和测试文件均已清理。Go 全量竞态测试和 `go vet ./...` 通过，双连接的撤销与到期用例连续三轮通过。[双靶机复现命令](../lab/README.md#检查撤销到期和已完成的修改)
